Overview

There are two deployment paths. Start with the static app; add the API only when a deployment needs live server-backed content. The app continues to show bundled lessons when the API is not configured or cannot be reached.

Static app

Expo exports the web client to dist/. The Pages workflow also copies this guide into dist/docs/, then publishes both from the same build.

Optional API
Build infra/Dockerfile.api from the repository root, connect it to PostgreSQL, and provide its public URL to the web build.

Keep course text and lesson metadata in the repository. Treat video and thumbnail URLs in the content seed as externally hosted assets; they still need to be reachable over HTTPS.

Publish the web app

The deployment workflow runs on pushes to main or master, and can also be started manually from the Actions tab.

1

Create the GitHub repository

Push this project to a repository named course-app. Use the default branch main. For free GitHub Pages hosting, make the repository public; Pages availability for private repositories depends on the organization or account plan.

2

Enable GitHub Actions for Pages

Open Settings → Pages, then set Build and deployment → Source to GitHub Actions. Do not select a branch-based publishing source.

3

Push to the deployment branch

Each push runs checks, exports the static app, adds this guide, and deploys the artifact. Check the Actions tab for the run result and deployed Pages URL.

API not configured?

Leave EXPO_PUBLIC_API_URL unset. The web app uses its bundled course content and does not require an API key or database.

Connect an optional API

When the API has been deployed and its HTTPS health endpoint responds, add a repository Actions variable named EXPO_PUBLIC_API_URL under Settings → Secrets and variables → Actions → Variables. Set its value to the API base URL ending in /api/v1, for example:

https://api.example.com/api/v1

This is a public URL, not a secret. The workflow reads the variable during the web export, so changing it requires a new deployment run. Also allow the Pages site origin in the API's ALLOWED_WEB_ORIGINS setting, without a trailing slash or path:

https://<owner>.github.io

For a project site, the origin does not include /course-app. For a user or organization site, use that site's .github.io origin.

Host the optional API

The NestJS API and PostgreSQL database run separately from GitHub Pages. Use a container host and a managed PostgreSQL service, or deploy the included Compose stack on a server you operate.

Container host or managed platform

  1. Build from the repository root with infra/Dockerfile.api as the Dockerfile. The repository root must be the build context because the image uses workspace packages and checked-in course content.
  2. Attach a PostgreSQL database and set DATABASE_URL to its connection URL. Use a private database connection where the provider supports it.
  3. Set PORT to the port expected by the host, and set ALLOWED_WEB_ORIGINS to the exact comma-separated list of website origins that may call the API.
  4. Run npm run db:migrate:deploy --workspace @course-app/api as a release step before starting the new container.
  5. Expose the service through the host's HTTPS endpoint. Configure its health check to /api/v1/health.
  6. Confirm the service is healthy, then set EXPO_PUBLIC_API_URL in the GitHub Actions variables and redeploy the web app.

The included Docker Compose configuration applies migrations on startup; other container platforms should run the command above as a release step. Back up the database before deploying schema changes. Keep production credentials in the hosting provider's secret store; never commit a populated .env file.

Self-host with Docker Compose

The included Compose configuration is intended for local development and self-hosting on a trusted machine. Start it from the repository root:

docker compose -f infra/docker-compose.yml up -d --build
docker compose -f infra/docker-compose.yml exec api npm run db:seed --workspace @course-app/api

For an internet-facing deployment, replace local database credentials, configure persistent storage and backups, restrict database access to the API, and put the API behind a TLS-enabled reverse proxy. Set ALLOWED_WEB_ORIGINS to the site origin. Do not expose the database port publicly.

Build mobile apps

The repository includes native Expo app configuration. GitHub Pages publishes only the web app; Android and iOS binaries require a separate build and distribution process.

  1. From the repository root, sign in and configure EAS. Run: 
    npx eas-cli@latest login
npx eas-cli@latest build:configure
  2. Set the production EXPO_PUBLIC_API_URL in the EAS build environment only if the native app should use the API. Otherwise, omit it and use bundled content.
  3. Build Android and iOS binaries, then submit them through the relevant app stores: 
    npx eas-cli@latest build --platform all

Store signing credentials and any server secrets in EAS or the API host, not in source control. Test a development build on real devices before distributing a release.

Release and operations

  • Before merging content changes, run npm ci, npm run content:validate --workspace @course-app/api, npm run lint, and the type checks documented in the repository README.
  • Inspect the Actions run after deployment. A successful app build does not verify the availability of external video, thumbnail, database, or API services.
  • Keep database backups and verify a restore procedure before relying on API-backed data.
  • Review course-content distribution rights separately from the MIT license for application code.
  • Progress and cached results are device-local. A server deployment does not enable learner accounts or cross-device synchronization.

Troubleshooting

Pages shows a 404 or an empty page

Confirm Pages uses GitHub Actions as its source, then check the Pages deployment job in the Actions tab. Wait for the deployment to finish before reopening the site.

The API is ignored or requests fail in a browser

Check that the Actions variable ends in /api/v1, trigger a fresh web deployment, and verify that the API's CORS allowlist contains the website origin exactly.

The API container fails to start

Check the database connection URL, network access from the API container, and migration logs. The host must allow the container to bind to the configured PORT.

Some lessons or media are missing

Run the content validator and verify that referenced lesson files exist and external media URLs are reachable over HTTPS.
